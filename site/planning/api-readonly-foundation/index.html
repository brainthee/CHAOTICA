    Plan: API foundation for a read-only UI experience¶

    Status: draft for review · 2026-10-15 · Owner: API track (CHAOTICA repo) Companion: /data/projects/chaotica_lcars (LCARS standalone UI track) · Gap analysis: /data/projects/chaotica_lcars/docs/API_GAP_ANALYSIS.md

    1. Goal¶

    Make /api/v1/ capable of driving a read-only experience of CHAOTICA's primary pages:

    • Dashboard (queues, alarms, stats, team, notifications)
    • Job and Phase detail pages and everything they link to (client, contacts, framework, people, org unit, service, billing badge, notes, activity, schedule)
    • Scheduler (global, job, phase) including live updates and change history
    • Skills / Services (+ qualifications) incl. the skill matrix and service coverage

    …and fix sign-in and the session-only middleware so a separately-hosted client (the LCARS UI) can use it safely.

    Non-goals (this plan)¶

    Writes (beyond mark-notification-read, see §6.4); admin/config surfaces (settings, imports, backups, notification rules, report wizard, RM sync) — those stay in the main UI and are reached via web_url deep links.

    Foundation principle — this is not throwaway work¶

    The long-term direction (see docs/frontend-migration-plan.md) is an API-driven main UI. So everything here is built as the API the main UI will eventually use, not an LCARS-specific API:

    • One versioned surface: /api/v1/ (additive changes only; no /api/lcars/).
    • Both auth modes are first-class: session + CSRF (same-origin main UI) and OAuth2 bearer (cross-origin clients).
    • Logic is extracted out of template views into shared layers that both the templates and the API call (§3). That is what keeps the coexistence period short and cheap.

    2. Current state (summary)¶

    /api/v1/ = 16 read-only resources + 4 HR/automation write actions + composite /schedule/. Permission-faithful scoping via the canonical managers (good — keep). No filtering, flat FK-id shapes, no capabilities, DRF authtoken only (no expiry/scopes, needs a local password), middleware ignores token users. Full detail: gap analysis §2–§3.

    3. Architecture for coexistence (templates + API)¶

                ┌──────────── template views (existing) ───────────┐
request ──► │                                                  │──► selectors (reads)  ──► models/managers
            └──────────── API viewsets (/api/v1/) ─────────────┘──► policy facade      ──► guardian/managers today, PDP later
                                                                 ──► services (writes, later)
    Layer Location (proposed) Rule
    Selectors jobtracker/selectors/<domain>.py, chaotica_utils/selectors/… Pure functions: (user, **filters) -> QuerySet/dict. Own the scoping + prefetch + any computed aggregates (dashboard queues, alarms, service coverage, skill matrix). Template views and API both call them.
    Policy facade chaotica_utils/policy.py can(user, action, obj) -> bool, scope(user, action, Model) -> QuerySet, capabilities(user, obj) -> dict, transitions(user, obj) -> list. Delegates to today's guardian/managers/can_to_*; becomes the seam for the planned in-process PDP (Lambda #58) — swap the implementation, not the callers.
    Serializers jobtracker/api/v1/serializers/ (split by domain) Representation only. No queries beyond what selectors prefetched. Field-level gating via policy.can (e.g. sales/loaded costs).
    Viewsets jobtracker/api/v1/views/ (split by domain) Thin: parse params → selector → serializer.

    Rule for every endpoint in this plan — "extract, then expose": the PR that adds an API endpoint for page X also refactors X's template view to call the same selector. Duplication therefore exists only in templates' rendering, never in query/permission logic. A short docs/development/api_coexistence.md lists any page still holding logic in its view (the debt register).

    Parity tests (coexistence safety net): for each migrated page, a test asserts the API list/detail scope equals the template view's queryset for a matrix of users (admin, unit manager, consultant, guest team member, outsider). Lives with the existing permission tests.

    4. API conventions (decide once, apply everywhere)¶

    Concern Convention
    Base classes New ApiViewSet / ApiReadOnlyViewSet in jobtracker/api/v1/base.py (extend current base): tz activation + current-user binding after DRF auth (§5.2), maintenance check, throttle scopes, error envelope.
    References Every FK rendered as a ref: {"id": 12, "display": "Daystrom Institute", "type": "client", "url": "/api/v1/clients/12/", "web_url": "https://…/client/daystrom/"}. One RefField used everywhere.
    Deep links Every object carries web_url (main UI) — lets read-only clients offer "Edit in CHAOTICA". Built from get_absolute_url() + configured base URL.
    List vs detail Light list serializer; rich detail serializer with small nested collections inline (team, links, contacts). Large/unbounded collections are sub-resources (notes, activity, timeslots) — paginated. No generic ?expand= in this plan.
    Capabilities Detail responses include "capabilities": {"view_sales": true, "update": false, …} and, for FSM objects, "workflow": {"status": 6, "status_display": "In Progress", "steps": [...], "transitions": [{"to": 7, "label": "Complete", "allowed": false}]} via policy. Read-only clients use them to show/hide sections now; write clients reuse them later.
    Filtering django-filter (already installed, 25.1) FilterSet per list + OrderingFilter + SearchFilter. Common filters: unit, client, status/status__in, involving=me, date windows.
    Dates/times ISO-8601 with offset; dates as YYYY-MM-DD; user tz exposed in /me/.
    Pagination Keep {count,next,previous,results}, page_size 50 / max 200.
    Errors {"error": {"code": "permission_denied", "message": "…", "fields": {…}}} via custom exception handler (v1 only).
    Feature flags Endpoints for disabled features (constance) return 404 + flag shown in /meta/.
    Sensitive data Field-level gating (can_view_loaded_costs, restricted jobs, competency data). PII decision needed (§9). Certificates/media never as raw MEDIA URLs.
    Performance Each endpoint has an assertNumQueries budget test (lessons from dashboard perf work: no per-row perm calls, Exists() over filtered prefetch).
    Schema / contract drf-spectacular; tags per domain; manage.py spectacular --file exported to docs/api/openapi-v1.yaml and checked in CI for drift. Endpoints marked x-stability: beta until the LCARS + main UI have consumed them.
    Stability Additive-only within v1; removals go through deprecation notes in docs/development/api_v1.md.

    5. Sign-in & middleware¶

    5.1 Middleware fixes (small, do first — independent of everything else)¶

    Verified issues (gap analysis F3/F4):

    # Problem Fix
    MW1 MaintenanceModeMiddleware reads request.user (session) before DRF auth → token callers 302'd to /maintenance/. Skip /api/ (and OAuth endpoints) in the middleware; enforce in ApiViewSet.initial() after authentication → 503 {"error":{"code":"maintenance"}} unless superuser.
    MW2 CurrentUserMiddleware captures request.user at middleware time → AnonymousUser for token requests → AuditEvent / TimeSlot / ScheduleAction attribution lost for API writes. Store the request (thread/contextvar) and resolve request.user lazily in get_current_user(). DRF's Request.user setter writes through to the underlying HttpRequest, so the authenticated API user is picked up. Use contextvars (ASGI-safe) rather than thread-local.
    MW3 TimezoneMiddleware sees session user only → token requests in UTC. Also activate tz in ApiViewSet.initial() post-auth.
    MW4 Token endpoint (/api/v1/auth/token/) ignores LOCAL_LOGIN_ENABLED; no throttling anywhere. Honour LOCAL_LOGIN_ENABLED; add DRF throttles (anon, user, auth burst scope on token/OAuth endpoints).
    MW5 CORS_ALLOW_ALL_ORIGINS = True, applies to every path. CORS_ALLOWED_ORIGINS from env (+ OAuth app redirect origins), CORS_URLS_REGEX = r"^/(api\|o)/".
    MW6 NewInstallMiddleware HTML-redirects API calls during setup. JSON 503 for /api/ while setup required.
    MW7 Impersonation + API. Session-authenticated API calls honour impersonation (main UI parity); bearer tokens never impersonate. Document.
    MW8 simple_history HistoryRequestMiddleware. Verify it resolves user lazily for DRF requests (expected OK); add a test.

    Tests: token-authenticated request during maintenance; audit actor on a token-authenticated write (use the existing set-status action); tz on token request; throttle; CORS preflight from allowed/disallowed origin.

    5.2 Sign-in design¶

    Two kinds of client, two mechanisms — both first-class, no throwaway:

    Client Mechanism Notes
    Main UI (same origin; templates' JS today, Vue SPA later) DRF SessionAuthentication + CSRF Already works. Unchanged login (ADFS / local).
    Standalone UIs (LCARS) and future third-party clients, cross-origin, any CHAOTICA instance OAuth 2.1 Authorization Code + PKCE, CHAOTICA as authorization server (django-oauth-toolkit) Public client, no secret. The "login" step is CHAOTICA's existing login page (so ADFS/Authentik/local all just work) → consent → redirect back with code → short-lived access token (~1h) + rotating refresh token. Scopes: read now; write, schedule:write later.
    Scripts / integrations Existing personal API token (DRF authtoken) Keep for now; later migrate to DOT personal tokens with expiry (separate item).

    Linking flow ("connect LCARS to a CHAOTICA site"): 1. User enters the instance URL in LCARS → GET {instance}/api/v1/meta/ (public) returns version, features, oauth: {authorize_url, token_url, client_id?}, ws_url, web_base_url, branding. 2. LCARS performs PKCE redirect to {instance}/o/authorize/ → user logs in via normal CHAOTICA login → consent screen ("LCARS wants read access"). 3. Tokens held in memory; refresh token rotation; profile page gets a Connected apps card (list/revoke), audited like API tokens today.

    Client registration: decision needed (§9). Proposal: a CONSTANCE/env-configured list of trusted first-party public clients (client_id + allowed redirect origins) so an admin enables LCARS per instance without the Django admin (respects the "admin is disaster-recovery only" rule) — exposed on the in-app Settings page.

    WebSockets: neither cookies (cross-origin) nor headers (browser WS API) work for bearer clients. Add POST /api/v1/realtime/ticket/ → single-use, 30-second ticket bound to user; connect with wss://…/ws/…?ticket=…; a TicketAuthMiddleware in the Channels stack before AuthMiddlewareStack. Works for session clients too (one path). Also fix Origin validation to use the CORS allowlist rather than ALLOWED_HOSTS.

    Rejected: accepting IdP (AAD/Authentik) access tokens directly — couples every client to each instance's IdP app registration, doesn't cover local accounts, and the main UI wouldn't use it. Hosting LCARS same-origin only — fine for dev (see §8) but defeats "link into any site".

    7. Phased delivery (milestones)¶

    Each milestone: selectors extracted + template view switched to them + API endpoints + permission-matrix, parity and query-budget tests + schema export + docs (docs/development/api_v1.md).

    # Milestone Contents Unblocks LCARS
    A0 Middleware fixes MW1–MW8 + tests. Small, standalone PR. —
    A1 Conventions & scaffolding ApiViewSet base, RefField/web_url, error envelope, throttles, CORS allowlist, filters infra, policy facade (delegating), split v1 modules by domain, schema export + CI drift check, api_coexistence.md debt register, test helpers (perm matrix / parity / query budget). Contract shape
    A2 Platform /meta/, /me/, /me/preferences/, /search/, /search/goto/. Shell, nav, capabilities
    A3 Jobs & phases §6.3 (minus schedule sub-resources). Job/phase pages
    A4 Dashboard §6.2 incl. alarms, queues, stats, team, notifications read + mark-read. Dashboard
    A5 Scheduler read §6.4 + job/phase/project schedule composites + actions history + deltas. Switch vis-timeline feeds to the shared selector. Scheduler (polling)
    A6 Linked entities §6.5. Click-throughs
    A7 Skills / services / quals §6.6. Skills/services pages
    A8 Sign-in & realtime django-oauth-toolkit (PKCE, consent, rotation, connected-apps card, Settings-page client config), WS ticket auth + ws/me/, Origin allowlist. Standalone deployment + live updates
    A9 Dogfood (main UI) Point the main UI's own JSON consumers at v1: scheduler vis feeds, notifications widget, global search, job/client DataTables lists. Retire equivalent legacy /api/ and ad-hoc JSON views. — (foundation for API-driven main UI)

    Order rationale: A0 is risk-free and fixes a live audit-attribution hazard. A1 sets conventions before endpoints multiply. A8 can run in parallel with A3–A7 (independent code) but must land before LCARS is deployed anywhere other than a developer machine. LCARS development is unblocked from A2 via same-origin dev proxy (§8).

    Rough size: A0 2–3d · A1 1w · A2 3–4d · A3 1.5w · A4 1w · A5 1.5w · A6 1w · A7 1w · A8 1.5–2w · A9 1–1.5w → ≈ 10–12 weeks single-track. These are estimates, not commitments.

    8. Working with the LCARS track¶

    • LCARS lives in /data/projects/chaotica_lcars (separate repo, separate Claude session). It never edits CHAOTICA; it may read CHAOTICA freely for reference.
    • Contract: the exported schema docs/api/openapi-v1.yaml (this repo) is the source of truth; LCARS generates TS types from it. This plan's §6 is the forward-looking contract until endpoints exist; LCARS mocks against it.
    • Requests from LCARS: /data/projects/chaotica_lcars/docs/API_REQUESTS.md — the API track reviews it at each milestone.
    • Status: at each milestone the API track updates /data/projects/chaotica_lcars/docs/API_STATUS.md (endpoint → status) and messages the LCARS session if it is running.
    • Dev auth before A8: LCARS dev server proxies /api, /ws, /auth, /oauth2 to the local CHAOTICA runserver → same origin → session auth works with zero backend changes.
    • Branching: API work on a feature branch per milestone (feature/api-a0-middleware, …) — the main checkout is shared with other sessions (see memory gotcha); stage explicit paths only.

    9. Decisions needed¶

    1. PII in the API — expose email/phone on user refs/profile cards (UI shows them) or keep the current "identity only" stance and add a contact block gated by view_user?
    2. OAuth client registration — trusted first-party clients configured on the Settings page (proposed) vs per-instance manual registration?
    3. Billing codes — confirm deferral until the scoping fix.
    4. Restricted jobs — today is_restricted is a flag + warning; confirm no additional field-hiding is expected for non-team viewers in the API.
    5. Vue SPA plan alignment — adopt this plan as Phase 0b/0c of docs/frontend-migration-plan.md (and update that doc: it assumes session-only auth and the legacy /api/ location)?
    6. Personal API tokens — leave as-is for now, or schedule migration to expiring DOT tokens?

    10. Incidental fixes worth bundling¶

    From the review (gap analysis §5), cheap and adjacent to this work: notification subscription endpoints always-400 (isinstance bug), follow_entity opt-out reading request.POST, user_feedback_summary permission gap, job_level_list login gate, ClientContactUpdateView perm, phase feedback edit/delete login, site search exposing all users. State-changing GETs (RM sync, notification rules) belong to Lambda #58's Phase 1 guard rails.
